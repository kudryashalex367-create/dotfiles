# ТЗ: агент для работы с дотфайлами (Arch Linux, bare-git)

## 0. Контекст
- Рабочая директория — $HOME. Репозиторий — bare-git: `config` = `/usr/bin/git --git-dir=$HOME/.cfg/ --work-tree=$HOME`. Ветка только `main`, remote `origin` (публичный GitHub-репозиторий).
- В репозитории `status.showUntrackedFiles = no`: новые файлы не видны в `config status`, пока их явно не добавили.
- Aider запущен с `--no-git` и `--yes`: собственных автокоммитов и `/undo` нет, подтверждений от человека нет. Единственная страховка — бэкапы (раздел 5) и твоя дисциплина.
- Если алиаса `config` в шелле нет — используй полную команду.
- Hyprland применяет конфиг сразу после сохранения файла. Сломанная правка ломает рабочий стол мгновенно, поэтому проверяй каждую правку сразу.
- Язык общения: русский, коротко и по делу.

## 1. Принципы
1. Делай ровно то, что просили. Всё, что заметил рядом (устаревшие опции, лишние пакеты, странные строки), не чини, а перечисли в конце отчёта.
2. Исключение: пользователь явно дал свободу («на своё усмотрение», «сделай что-нибудь крутое»). Тогда инициатива разрешена только внутри названного файла или секции.
3. Любая правка обратима: бэкап → правка → проверка → diff.
4. Сомневаешься в задаче — один короткий вопрос, а не догадки.

## 2. Уровни доступа
| Уровень | Что разрешено | Когда |
| :-- | :-- | :-- |
| L0 чтение | `cat`, `head`, `grep`, `ls`, `wc`, `diff`, `config status/diff/log/show/ls-files/branch`, валидаторы из раздела 6 | всегда |
| L1 правка | редактирование файлов внутри $HOME + бэкап | по задаче пользователя |
| L2 локальный коммит | `config add -- <файлы>`, `config commit` | только по просьбе («закоммить») |
| L3 сеть | `config fetch/pull/push`, `cpush`, `cpull` | только по явной просьбе в текущем сообщении |

Разрешение не переносится: «запушь» действует один раз и не означает «пушь и дальше».

## 3. Абсолютные запреты
Без явной команды пользователя в текущем сообщении нельзя ничего из этого списка. Секреты нельзя ни при каких условиях.

**Git**
- `config add -A`, `config add .`, `config add -f`, `config commit -a/--all`, `config commit --amend`
- `config push --force`, `-f`, `--force-with-lease`, `--tags`, push в любую ветку кроме `main`
- `config reset` (любой режим), `clean`, `checkout -f`, `checkout .`, `restore .`, `stash`, `rebase`, `rm`, `gc`, `prune`, `reflog expire`, `filter-branch`
- `config remote ...`, `config config ...` (в том числе не трогай `status.showUntrackedFiles`)

**Система**
- `sudo`, `pacman`/`yay` на установку или удаление, `systemctl`, `chsh`, `rm -rf`, `kill`/`pkill`
- выход из сессии (`niri msg action quit`, `hyprctl dispatch exit`)
- правка файлов вне $HOME

**Файлы**
- Не удалять, не переименовывать, не переносить файлы. Исключения: свои бэкапы и файл, который ты сам создал в этой сессии, если пользователь просит откатить.
- `.config/pkglist_*.txt`, списки пакетов, конфиги WM и сессий, не упомянутых в задаче, не трогать.

**Секреты**
- Не читать, не выводить в чат, не копировать в бэкап, не коммитить: `~/.zshrc_secrets`, `~/.ssh`, `~/.gnupg`, внутренности `~/.cfg/`, любые файлы с `secret`, `key`, `token`, `credential`, `password` в имени, `.env`.
- Не печатать переменные окружения (`env`, `printenv`, `echo $OPENAI_API_KEY` и т.п.).

## 4. Протокол задачи
**0. Preflight (один раз за сессию)**
- `config branch --show-current` (должно быть `main`) и `config status -sb | head -20`.
- Tracked-файлы, изменённые ещё до тебя, считай «чужими»: не откатывай их и не коммить вместе со своими.
- Выбери каталог бэкапа `B=$HOME/dotfiles-backup/aider/<YYYY-MM-DD_HHMMSS>`, создай его и дальше подставляй буквальный путь (переменные между командами не сохраняются).

**1. План** в одну-две строки: какие файлы и что меняем. Если файлов больше 8 или правок больше ~300 строк суммарно, покажи план и дождись подтверждения. Если пользователь сам перечислил все файлы, подтверждение не нужно.

**2. Перед первой правкой каждого файла F** (путь относительно $HOME)
- Отслеживается ли: `config ls-files --error-unmatch F`.
- Был ли изменён до тебя: `config status -s -- F` (не пусто — был).
- Бэкап: `cp --parents F "$B/"`.
- Размер: `wc -l F`.

**3. Правка** в diff-формате.
- Не переписывай файл целиком.
- Не трогай отступы, порядок и комментарии вне затронутых строк.
- Где правка неочевидна, оставь короткий комментарий в стиле файла.

**4. Страж размера.** После правки снова `wc -l F`. Если строк стало меньше 70% от исходного, а удаление не просили, сразу откат из бэкапа и отчёт.

**5. Проверка** по таблице раздела 6.
- Не прошла: одна попытка починить.
- Снова не прошла: откат из бэкапа и отчёт с текстом ошибки. Больше двух попыток не делай.

**6. Diff.** Для каждого файла `diff -u "$B/F" F`. Он показывает ровно твои изменения, даже если файл был «грязным» или не отслеживается. Для сводки добавь `config diff --stat`.

**7. Отчёт** (раздел 10). После него остановись и жди. Следующую задачу сам не начинай.

## 5. Бэкап и откат
- Один каталог на сессию, один бэкап файла за сессию (при первом касании). Старые бэкапы не чисти.
- Основной откат: `cp "$B/F" F`. Он возвращает файл ровно в состояние до тебя, включая чужие незакоммиченные правки.
- `config restore -- F` используй только если файл был чистым до тебя и пользователь просит вернуть его к HEAD. Иначе потеряются его незакоммиченные изменения.
- Чекпоинт-коммитов не делай: они засоряют публичную историю, бэкапа достаточно.
- Если файл создан тобой в этой сессии, бэкапа нет. Откат = удалить именно этот файл, и только по просьбе пользователя.

## 6. Проверка по типам файлов
| Файл | Проверка |
| :-- | :-- |
| `.config/niri/*` | `niri validate` |
| `.config/hypr/hyprland.*` | `hyprctl configerrors` (пусто = ок). Ручной reload не нужен: применяется само |
| `.zshrc`, `*.zsh` | `zsh -n <файл>` |
| скрипты в `.local/bin` | `bash -n` или `zsh -n` по shebang; `shellcheck`, если установлен |
| `.config/mako/*` | `makoctl reload`; ошибка → откат |
| `*.json` | `jq . <файл>` |
| `*.toml` | `python -c 'import sys,tomllib;tomllib.load(open(sys.argv[1],"rb"))' <файл>` |
| остальное (kitty, fuzzel, hyprlock и т.д.) | автопроверки нет. Скажи об этом прямо и напиши, как проверить глазами |

Не запускай `hyprlock` для проверки (заблокирует экран) и не перезапускай композитор и сервисы.

## 7. Git

### Коммит (L2)
Только по просьбе.
1. Свои файлы: `config add -- F1 F2`. Новый файл — только если пользователь просил взять его под контроль. «Чужие» файлы не добавляй.
2. `config diff --cached --stat` должен показывать только ожидаемые файлы. Лишнее убери через `config restore --staged -- <файл>`.
3. Проверка на секреты в добавленных строках:
   `config diff --cached -U0 | grep -E '^\+' | grep -Eiq '(api[_-]?key|secret|token|passw|bearer|sk-[A-Za-z0-9]{10,}|ghp_|BEGIN [A-Z ]*PRIVATE KEY)'`
   Совпадение → стоп, `config restore --staged`, сообщи пользователю.
4. `config commit -m "<область>: <что>"`. Перед этим глянь `config log --oneline -5` и повтори стиль и язык сообщений. Не больше 72 символов, без `-a`, без `--amend`, без слов «checkpoint» и «aider».

### cpush (L3)
Только по явной просьбе («запушь», «cpush»). Функция `cpush` делает `config add -u`, то есть коммитит все изменённые tracked-файлы, включая чужие. Поэтому:
1. `config status -s`. Если изменённые tracked-файлы входят в список файлов этой сессии, можно вызвать `cpush "<msg>"`.
2. Если есть лишние файлы, покажи их и спроси: «всё или только мои?». Если «только мои», не вызывай `cpush`: сделай шаги из «Коммит» и затем push (п. 4).
3. Проверка на секреты (шаг 3 из «Коммит») обязательна до push. Для `cpush` запускай её на `config diff HEAD -U0`.
4. Явный push (без зависаний на запросе пароля):
   `GIT_TERMINAL_PROMPT=0 timeout 60 /usr/bin/git --git-dir=$HOME/.cfg/ --work-tree=$HOME push origin main`
5. Отклонён (non-fast-forward) — не форси. Сообщи и предложи `cpull`. Ошибка авторизации — не повторяй, сообщи.
6. После успеха: `config status -sb | head -3` и `config log --oneline -3`.

### cpull (L3)
Только по явной просьбе. Функцию `cpull` не вызывай: она заканчивается `exec zsh`, который подменит шелл агента и может повесить сессию. Делай так:
1. `GIT_TERMINAL_PROMPT=0 timeout 60 /usr/bin/git --git-dir=$HOME/.cfg/ --work-tree=$HOME fetch origin main`
2. `config diff --stat HEAD FETCH_HEAD` — покажи, что придёт. Если среди файлов есть те, что изменены локально (`config status -s`), стоп и вопрос.
3. Иначе: `GIT_TERMINAL_PROMPT=0 timeout 60 /usr/bin/git --git-dir=$HOME/.cfg/ --work-tree=$HOME pull origin main --no-rebase`
4. Конфликт: ничего не резолви сам, выполни `config merge --abort`, перечисли файлы, жди указаний.
5. После pull: перечисли изменившиеся файлы, прогони для них проверки из раздела 6 (только отчёт, ничего не чини) и напиши, что нужно перезагрузить. Если менялся `.zshrc`, скажи пользователю выполнить `exec zsh` самому.

## 8. Когда остановиться и спросить
- Нужен файл вне $HOME, `sudo`, или файл из списка секретов.
- Нужно удалить, переименовать или переместить файл.
- Задача больше лимитов (8 файлов / ~300 строк) и файлы не были перечислены пользователем.
- Проверка не прошла после двух попыток.
- Push отклонён, ошибка авторизации, конфликт при pull.
- Нужна команда, которой нет в L0–L3.
- Непонятно, что именно просили.

Если файл был изменён до тебя, предупреди одной строкой и продолжай: бэкап тебя страхует.

## 9. Экономия и лимиты
- Не запускай команды «на всякий случай». Длинный вывод режь: `| head -50`, логи `| tail -30`.
- Нужна секция, а не весь файл: `grep -n`, `sed -n 'A,Bp'`.
- Не добавляй в чат файлы, которые не правишь.
- Не повторяй проверки, которые уже прошли и после которых файл не менялся.
- Если на задачу нужно больше ~15 команд, остановись и объясни, почему.

## 10. Формат отчёта
```
Сделано: <1–2 строки>
Файлы: <список> (бэкап: <путь B>)
Проверка: <команда → результат | «автопроверки нет — глянь вручную: ...»>
Diff: <diff -u или --stat>
Откат: cp "<B>/<F>" <F>
Заметил, но не трогал: <список или «—»>
Дальше: <закоммитить? запушить? — одним вопросом>
```

## 11. Критерий успеха
Файл изменён только в запрошенных местах, проверка пройдена (или честно сказано, что её нет), `diff -u` показывает только ожидаемые строки, бэкап лежит на месте, ничего не закоммичено и не запушено без просьбы, пользователь подтвердил результат.
